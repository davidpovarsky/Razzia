## Finding — P2: existing database inspection accepts structurally different SQL schemas

`first-party/schema.ts:36–59` checks `user_version`, rollback journal mode, exactly one owner/version row, `quick_check(1)`, and whether three `SELECT ... LIMIT 0` queries can be prepared. Those checks do **not** verify actual table definitions, required primary/unique/check constraints, indexes or unexpected triggers. A synthetic preexisting database can present the required column names and owner/version while omitting the `operations` primary key or `native_id IS NULL` constraint, or while adding a trigger; `quick_check` alone does not require it to match the schema created in `initialize`. The existing audit-failure test deliberately creates a trigger, which is consistent with the inspector allowing triggers; it does not demonstrate malicious execution.

The service-owned directory and no hostile-OS-race assumption limit exposure, and the adapter itself inserts `native_id` as NULL and rejects a non-NULL replay. This finding is about accepting an unexpected existing schema as version 1, not a claim of current cross-tenant compromise or live publication. A wrong/legacy/modified database can satisfy the current inspection while omitting the on-disk invariant, undermining the stated fail-closed treatment of unexpected schema and the guarantee being attached to it. Bind inspection to the exact supported schema/constraints/indexes and an explicit trigger policy, or use another robust, versioned schema attestation with migration/recovery excluded from GET. Preserve bytes and reject unknown schema without repairing it. Add focused negative fixtures for a same-column table missing the NULL/uniqueness constraints and an unexpected mutating trigger; check GET and mutation denial and unchanged data. Do not silently migrate or alter an existing customer database.

## Cancellation boundary — decision and witness needed

`first-party/ingress.ts:107–171` correctly retains the ingress slot while a body read and its cancellation settle. In `first-party/http.ts:66–103`, after the body completes, `auth.principal(c)` is awaited, but `request.signal` is not checked again before opening the private store or before mutation. A request aborted during that later await can therefore continue to the synchronous transaction if its session remains valid. The README accurately says cancellation does not undo committed work, but it does not specify whether an abort observed **before** private mutation is meant to prevent starting that mutation. This is a source-level contract gap, not proof that a client abort guarantees rollback or that an in-flight/committed write can be safely undone.

Decide the intended semantics. If pre-mutation cancellation is required, recheck the actual signal after each asynchronous authentication boundary and immediately before starting private work, preserving the bounded lifetime and not claiming cancellation rolls back already committed rows. Otherwise explicitly document that cancellation after body completion may still start and commit an idempotent private mutation. A controlled actual-JWT HTTP witness should abort after complete body read while final authentication is held, then assert the chosen response and exact draft/operation/audit state. No network-facing endpoint or account mutation outside synthetic fixtures is needed.
