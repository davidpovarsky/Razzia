## Findings

### P1 — Successful save/export cannot replay after the draft advances

`extensions/src/mcp-app/server/dispatch.ts:32-53,166-204` checks the *current* draft revision before invoking the storage/export adapter. A successfully committed save at revision 1 followed by a valid edit to revision 2 means an identical retry of the original idempotency key and payload returns `REVISION_CONFLICT`; the adapter never gets a chance to retrieve its authorized prior outcome. The same applies to export. This conflicts with M1 security acceptance `M1_SECURITY_ACCEPTANCE_20261115.json:1945-1959,2108-2110`: replay must reauthorize, same payload returns same authorized outcome, and the durable key/outcome mapping must survive retry. A client that lost the first response cannot discover the already-created result using the same key. Fix boundary: after current principal/grant/scope verification, have the authoritative durable idempotency service atomically check account+grant+tool+key+input digest and return an existing authorized outcome before requiring the current revision; on a new outcome validate the exact revision and consent in the same transaction/operation. Do not skip revoke, ownership, payload mismatch or consent checks, and do not introduce a global replay cache.

Executable witness: `adversarial.ts`, real SDK client/server linked transport and synthetic store/adapters: first save and export succeeded; revision 1→2 edit succeeded; both identical retries returned `REVISION_CONFLICT`; adapter invocation counters remained 1 each. Synthetic adapters here are deliberately simple, so the witness does not establish durable adapter behavior; it establishes that the dispatch precondition prevents *any* correct adapter from resolving this retry.

### P1 — SDK schema rejection runs before the authorizer and application rate limiter

`server/factory.ts:51,65-70` gives the real SDK the strict input schema; the SDK validates before calling `dispatch`, and the only injected `authorize`/principal rate-limit path is inside `dispatch.ts:72-81` and `authorization.ts:53-79`. An invalid `get_game_draft` with an unknown property returned SDK `isError` text `Input validation error ... Unrecognized key` with **zero authorizer calls**, **zero rate-limit calls**, and no structured MCP0.1 error envelope. The synthetic property name was reflected; its value was not. Thus malformed traffic bypasses this foundation's per-principal limiter and its consistent sanitized errors. The future HTTP boundary is separately required to authenticate, enforce body/Origin/HTTPS and implement pre-auth rate limiting; it is currently absent, so do not mistake it for protection already present. Fix minimum boundary: enforce authentication and appropriately keyed bounded pre-validation throttling at the transport/protocol boundary, and ensure invalid schemas produce safe, bounded contract-compliant errors without reflecting arbitrary keys or inputs. Verify this with the real SDK using an invalid unauthenticated request and a denial counter, not just a direct `dispatch` invocation; preserve strict schema discovery. Resource listing/reads are currently static public schema/guide/empty UI, not private data, but their eventual transport access must also obey the approved authentication policy.

### P2 — Stored draft's validated content and returned summary can disagree

`dispatch.ts:32-47,124-135` re-normalizes `record.authoredShowJson` and checks canonical bytes, but discards the computed summary and returns `record.summary`. A synthetic repository returning canonical valid `Synthetic test` content alongside `Different stored summary` was accepted; `get_game_draft` returned both inconsistent values as success. An accidental stale/corrupt summary can mislead the model/user and downstream preview checks. Fix: on read derive the summary from the authorized normalized authored content (and validate any necessary persisted metadata) or compare the stored summary to the independently recomputed one and fail closed. Add a linked-transport corruption witness; do not trust an adapter-provided summary solely because its shape parses.
