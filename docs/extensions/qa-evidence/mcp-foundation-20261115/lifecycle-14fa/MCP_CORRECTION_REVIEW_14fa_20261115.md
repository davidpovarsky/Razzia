## Required corrections

**1 · Request lifecycle across cancellation.** Source finding, corroborated against the installed SDK. In `extensions/src/mcp-app/server/connection.ts:75–95,100–104,119–141`, a tool request occupies a pending slot before asynchronous authorization. Successful dispatch binds the principal to its request ID. Normal cleanup relies on sending the response or closing the connection. The actual 2.4.0 server runtime `dist/src-DdvbAHrR.mjs:6348–6351,6519,6546,6562,6575` registers a request abort controller, suppresses both success and error responses after abort, then clears its own controller. A user cancelling a slow tool can therefore leave the wrapper's slot and authorized principal retained after the handler settles. Over the life of a connection, capacity can be lost until legitimate calls cause the connection to close. I found no evidence of cross-account disclosure. This is a static lifecycle finding; the independent concurrency test used ordinary valid reads.

There is a second timing case in the same fix. A cancellation delivered while authorization is pending can reach the SDK before its controller exists. Also, the guard clears the maps on close but its asynchronous rejection path can still try to send an error on a closed transport. Preserve the SDK's cancellation behavior across the admission step. Give each admitted operation a distinct lifetime bound to that connection and request, retire request/principal state through cancellation, completion and close, and reject late continuations from a retired lifetime. Count still-running dependency work until it actually settles, so a cancelled operation cannot free a slot for unlimited outstanding verification. Identity-check cleanup so an old completion cannot retire a newer request with the same ID. Correlate cleanup to the owning operation across tool and other SDK responses. Keep the private SDK untouched.

Acceptance for the correction: use bounded, read-only synthetic lifecycle cases. Verify clean completion and restored capacity for a normal client cancellation while admission is pending and while a handler is running. Verify duplicate active IDs close the owning connection, closing during authorization performs no later dispatch/send, a rejected send/close emits a safe error and leaves consistent terminal state, and another factory is unaffected. The 27 producer cases demonstrate ordinary guard behavior but do not establish these lifecycle cases. An already committed legitimate side effect does not acquire rollback semantics from cancellation.
