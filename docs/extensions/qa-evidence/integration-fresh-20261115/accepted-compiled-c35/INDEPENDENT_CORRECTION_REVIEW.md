## Findings

1. **P2 — Reserved hash-cycle paths are compared case-sensitively and file/directory prefix collisions are not rejected.** `compiled-index-schema.ts:320–354` checks case collisions *among listed files*, but excludes only exact lowercase `artifact-index.json`, `registry.json` and `accepted-pin.json`. A single `Artifact-Index.json` or `REGISTRY.JSON` is not equal to the reserved lowercase literal and has no listed peer with which to collide. On a case-insensitive filesystem it aliases the reserved index/registry name. Similarly paths such as `a` and `a/b` are distinct strings and pass the case check although they cannot both be regular files in one tree; the map-based validator accepts separate byte entries. Reject reserved names using the same case-folding policy and reject file/ancestor collisions, including case-folded variants. Apply a consistent rule to package/source path collections where their later materialization assumes the same filesystem. Add isolated adversarial witnesses; this is a structural diagnostic gap, not proof that a loader currently resolves either path.

2. **P2 — Declared source revision is not bound to its Git source records or recipe.** The artifact index declares `source.gitCommit` and each tracked source and `toolchain.buildRecipe` separately carries `gitCommit` (`compiled-index-schema.ts:155–161,306–318`). The artifact refinement checks the package lock (`:355–365`) but does not require tracked sources or recipe to use the declared commit, or the recipe to be part of the declared source set. Consequently a record can assert one top-level revision while listing inputs or a recipe from another revision and still parse; `compiled-index-validation.ts` checks that resource source records appear in the list, not that they agree with the declared revision. Define and enforce the intended repository/commit binding and exact recipe membership, or explicitly represent multiple repositories/revisions and prevent a single-revision provenance claim. Reject duplicate/case-aliased source identities according to that policy. This is a false-consistency risk in provenance diagnostics, not evidence that forged Git input is trusted for execution.

3. **P2 — Unexpected evidence keys are not bounded or typed before diagnostic output.** `compiled-index-validation.ts:48–65` limits map entry count and byte-array totals, but does not validate the type, encoding or length of each evidence key before interpolating it into `unexpected-file:${path}`. One unexpected key can be an arbitrarily large string or a non-string with user-controlled conversion, even though declared artifact paths have a 240-character strict schema. This bypasses the intended bounded diagnostic surface and can produce oversized output or throw during formatting. Require an ordinary bounded string path satisfying the same path policy before interpolation; reject invalid evidence keys rather than stringify arbitrary objects. If hostile JavaScript objects are in scope, also avoid relying on overridable Map iteration/getters or document the caller boundary explicitly. No file read, network action or authority grant was observed.
