## Physical namespace and binding

The coordinated namespace is the exact trusted physical show-storage root containing `quizz`, `extensions/quizzes`, media used by those shows, and their recovery families. Capture accounts flag, configured root and exact authenticated owner before lookup/allocation; reject missing enabled owner rather than inherit `resolveTenantFile`'s global fallback. Preserve case. Cross-check canonical path components and device; no path alias, client root or client token supplies authority. Accounts-off is explicit `legacy-global`, never an account-durability claim. Namespace equality is physical-root equality, not a REST route name or logical quiz ID. Existing results/auth/billing databases are not made durable by this gate; their unrelated namespaces must be explicitly excluded rather than silently advertised as protected.

An optional downstream `WriterPort` is installed only by actual native composition. Every participating native writer acquires it for its **complete synchronous mutation**, including preflight and final fences. Read-only helpers may not normalize IDs or create directories outside that operation. A leaf guard that checks once and releases before `write/unlink` is insufficient. Generic Map package staging keeps its callback contract and omits the native gate; no physical `quizz` mirror or missing-file fallback is added.

## Evaluate built-in SQLite coordination

Node's built-in `node:sqlite` is already used here; no daemon/dependency/system setting is needed. A private service-owned coordination database is a viable candidate for **cooperating** mutual exclusion: SQLite permits one write transaction, and `BEGIN IMMEDIATE` attempts that writer lease up front. Use strict busy/error handling and a qualified local filesystem; do not spin or hold the event loop waiting across unrelated async work. The [SQLite transaction contract](https://www.sqlite.org/lang_transaction.html) and [Node 24 DatabaseSync API](https://nodejs.org/docs/latest-v24.x/api/sqlite.html#new-databasesyncpath-options) support this candidate, not an already executed proof.

Required invariants before implementation:

1. **No SQL rollback claim for FS.** Rolling back a database transaction does not undo a hard link, file write, rename or unlink. The C1/Media journal remains the exact filesystem ownership/recovery authority.
2. **Persist a dirty/quiescent marker before FS mutation.** If the only marker is uncommitted in the same SQL transaction as the mutex, SIGKILL rolls it back and another process can enter while filesystem effects remain. Establish the durable pending operation first, then hold the live writer transaction; the intervening release/reacquire interval is safe only because other processes see the pending marker and refuse entry. Record operation nonce, trusted namespace and recovery-family identity, not guessed orphan data.
3. **Finish ordering.** Durable FS resolution/committed phase precedes clearing the coordination marker. Clear/fence the marker before releasing the final compatible recovery evidence; if SQL commit/fence fails, keep the last copy/intent and block dependent writers. Treat SQLite/directory-fsync errors as unresolved, not success. Qualified rollback phases permit only private cleanup after later customer edits.
4. **Nested calls are not blanket authority.** A process-private ownership token may authorize expected participant calls, but AsyncLocalStorage inheritance alone cannot legitimize arbitrary reentrant native CRUD invoked inside a filesystem callback. Bind namespace, operation kind, expected IDs and phase; reject active participant recursion, foreign tokens and consumed scopes. C1 never needs to invoke mutating native getters/CRUD during preparation, so those mutations must be denied while its operation owns the lease.
5. **Startup and another process.** Acquire the actual coordinating lease before replay; a successfully acquired SQLite writer lock after process death does not itself prove clean FS state. Inspect the durable pending marker and compatible journal, fence/resolve or remain quiescent. No PID-only stale-lock deletion. Retain readers through verified drain.
6. **Scope completeness.** C1's dedicated registry discovers its own explicit owners across flag changes. It does not discover historical per-tenant Media/V2 journals. For those families, propose a separate read-only trusted-owner source before claiming all roots: e.g. a bounded new `account-db.ts:listRecoveryOwners(configuredRoot)` opening an existing account database read-only, without schema setup, chmod, credentials changes or account-enabled global fallback. Validate exact owner spelling including disabled accounts. Missing historical owners remain an explicit unresolved discovery gate; never infer authority by recursively scanning customer shows. This additional protected symbol/path is NOT leased now.

SQLite's local write lock is a candidate portable cooperating-process primitive, not a distributed lock, reader isolation, hardware power-cut result or immunity to nonparticipating processes. A lock-directory alternative requires safe stale-owner/restart semantics and cannot be declared equivalent by deleting an old directory. The manager must approve the exact bridge, participant set, database/fence profile and lease deltas before B source edits.

Validation after A and new lease: force contention from real native CRUD and ID-assigning getters in a second process; nested permitted sidecar calls vs forbidden reentrant writes; zero-reference Media/delete/upload final-write fast paths; crash after dirty marker, during FS mutation, visible commit/fence failure, SQL clean failure and cleanup; trusted startup over explicit global/tenant roots. Keep Map stage positives and R2 ownership/digest evidence. These are prepared acceptance requirements, **not executed results**.
