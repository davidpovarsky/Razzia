## Live process measurements required before acceptance

`pid_observer.proposed.py` is a concrete host-only sampler, AST-parsed but never executed against a running container. The eventual controller must resolve the live owned init PID's exact cgroup, verify CID membership, then read `pids.current/max/events`, local events and peak when available, plus owned process PID/PPID/NSpid/state/threads/start time and resource limits. It records parent transitions and zombie counts; parent-controller reads contain only limits/counters. No unrelated process command lines/environment, container exec or extra observing PID is needed. Kernel PID-controller counters distinguish limit events from a transient/racy process snapshot. [Kernel cgroup v2 PID controller](https://docs.kernel.org/admin-guide/cgroup-v2.html#pid).

Integrate the sampler into the host monitor before source preflight, before/after each job, each running/terminal sample, at quiescence and **before stop destroys the cgroup**. Persist the measured snapshot before evaluating bounds. Require actual pids.max 96, initial max-event count zero, no new owned max events and the existing disk/log/time bounds. A new limit event is an infrastructure stop, not permission to raise the cap. Capture ancestor limits/counters and owned `Max processes` limits so an unexplained errno 11 is not automatically blamed on pids.max. Short-lived peaks can be missed by polling; cumulative events/available peak and raw Go stderr provide separate evidence.

Before each stage and after termination, require a bounded five-second **harness-only drain** to the original supervisor process identities and zero zombies, without sending cleanup signals or resetting counters. This does not widen any child/test timeout. A failed drain stops later work and preserves actual ownership/parent/thread records. Record races explicitly; summed process threads are not asserted equal to an atomic cgroup snapshot. No observed orphan/thread count is manufactured from PID numbering gaps.
