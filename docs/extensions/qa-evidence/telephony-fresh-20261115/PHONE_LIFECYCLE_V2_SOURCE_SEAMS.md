## Minimal proposed seams and alternatives

1. **Protected entry seam:** packages/socket/src/api/extensions/game-routes.ts, exported gameExtensionRoutes chain: one import/mount for an additive downstream v2 factory with injected requireManager/owned-Game resolver; a separate early legacy `/pilot-phone` mode guard rejects v1 writes to a v2-adopted game. Neither hunk is covered by S02 approval. Keep resolvePilotTargetGame and existing v1 semantics for legacy games; no rewrite of all routes or shared SessionClaims.
2. **Downstream implementation proposal:** new extensions/src/server/phone-lifecycle-v2/** plus an explicit public server/index.ts export, under a new exclusive lease. Own service leases, canonical request validation, SQLite CAS/idempotency/retirement, operation receipts and an injected Game port. No new package/common wire schema or framework dependency is necessary for this HTTP-only proposal.
3. **Facade alternative first:** build the Game port from existing public methods in the protected entry composition. Serialize v2 operations per owner/game and bind store validation plus synchronous controller projection to that executor. V1 is denied for adopted v2 games so it cannot bypass the facade. Manager removals/kicks invalidate an observed roster/client binding; do not silently create a replacement. Missing Game/roster means fail closed, not guessed cleanup/rebind.
4. **Unavoidable-hook candidate only if proven:** if actual admission/projection cannot provide the required atomic boundary through composition, request a precise new prepare/admit/commit port at GamePhoneController.joinOrRebindPhoneCaller and its Game constructor binding, with failure/crash witnesses. No blanket controller lease. Do not wrap a heap mutation in SQL and pretend SQL rollback undoes emitted events or roster changes. A full durable game/score engine is a substantially larger alternative and is not the minimal lifecycle scope.
5. **Gateway proposal:** pilot-runtime request dispatch gets an explicit versioned registration client and new private journal adapter, rather than altering v1 wire meanings. Journal registrationRequestId and scope before first dispatch; persist registration/generation/capability before using it. Store capabilities under an approved private root with an approved key/recovery mechanism, fsync/atomic publication and restrictive permissions. Current in-memory live/closedCalls maps remain only caches. No journal path/key/global configuration is provisioned now.

## Service/account/game binding and restart contract

An authenticated owner provisions a limited opaque service lease bound server-side to `(ownerAccountId, issuerSid, gameId, providerNamespace, serviceId, allowedActions, expiry, protocol=2)`. Owner/game relationship comes from the verified claim and actual Registry. Gateway receives the service capability once through an approved channel; store only its hash server-side. It cannot call unrelated manager APIs. Every registration/operation validates lease revocation/expiry, active account/session and game ownership before touching private lifecycle state. Provider namespace must match configured adapter/service context, not an arbitrary callback field. This authenticates a service, not a PSTN caller.

The proposed dedicated SQLite is owned by the lifecycle module, separate from accounts/billing. Store identity includes owner+game+provider namespace in every primary key/query. Resolve the storage location from an already verified explicit owner (or a root database with mandatory composite tenant keys); reject missing/invalid scope. Do not silently call getPath under absent AsyncLocalStorage ownership and receive global fallback. Actual storage path/migration/retention ownership must be approved before writes to customer installations.

Gateway durable recovery must preserve the trusted service lease, registrationRequestId, game/owner/provider scope and per-call capability. The same idempotent request is retried after uncertain registration outcome; a retry never mints a new registration request. Missing/corrupt journal/capability returns recovery-required and refuses automatic rebind. Phone plus old raw CallId is insufficient recovery proof. Reusing a raw provider ID for a genuinely new call requires verified new-attempt evidence or explicit trusted disposition; unknown retry/reuse guarantees remain unknown. Do not choose a longer numeric TTL as a substitute.

## Server-registration precedence and CAS

Draft new v2 REGISTER includes a trusted registration request ID, exact scope/caller correlation, and expectedPredecessorGeneration. Backend transaction deduplicates request ID+payload fingerprint, compares the current predecessor, and allocates the next monotonic generation with a random registration ID/capability. Initial expected generation 0 succeeds only if no binding exists. A stale expectation returns conflict without automatically refreshing and retrying it as a newer registration. B may replace A only through an explicitly authorized registration referencing the approved predecessor. No sorting opaque IDs or trusting ApiTime.

If A and B both expect 0 and B reaches the server first, B wins and late A conflicts. That is server-registration precedence, not a deduction about which physical call began first. If A is registered first, a new B must explicitly reference A's committed predecessor through trusted ingress; an old A operation cannot acquire a fresh generation by polling. Where the producer cannot distinguish a new call from a replay, fail closed pending proof/disposition.

All POLL/ANSWER/HANGUP operations carry server registration ID, generation, per-call capability and operationId; ANSWER also carries the current epoch. Poll never registers/rebinds. Operations require current active generation, exact owner/game/roster binding and service lease. Stale A hangup may close A's own terminal record but cannot disconnect or finish B. Return actual effect/idempotent outcome, not an invented successful mutation.

## Durable receipts versus in-memory projection

Proposed records: service_leases, registrations, current_bindings, retired_reference markers, registration/operation receipts and projection journal. Use atomic unique keys/CAS in a dedicated transaction. A backend abort/HTTP timeout can follow a committed mutation; reconcile the same operation receipt rather than issuing a fresh registration/answer.

Current Game/controller/round state is in memory. Therefore store reservation, heap projection and response are not one durable transaction. Proposed bounded coordinator records RESERVED/PENDING, executes through its serialized real Game port, then records observed APPLIED/REJECTED outcome. Crash windows require explicit UNKNOWN/PENDING handling. Do not auto-replay a possibly scored answer after restart, revive an older generation or claim rollback of heap effects. When the actual Game cannot be restored, deny the old game/capability and retain unresolved outcome; never target a newer global room. Exactly-once score recovery across full backend loss requires a separately approved durable canonical game ledger, not this minimal seam.

Registration admission failure/projection failure must be specified before code: do not publish a usable capability before admission/projection succeeds; terminal predecessor retirement cannot be casually undone. Prototype real admission+CAS+crash witnesses first. If a pending projection is ambiguous, block operations and require explicit reconciliation. This is the principal critical-review boundary for choosing facade versus a tiny prepare/commit controller port.

## Legacy policy and acceptance matrix

Recommended rollout is new explicitly adopted games only, v2 feature off by default. Legacy games keep S01/S02 behavior and their known remaining lifecycle limitations. A v2 game denies v1 phone writes with a version-required response; no in-place migration of an active game/caller is implicit. Old API11 is retained as legacy physical-order failure unless provider evidence or explicit new-version migration disposition resolves that product requirement. No production rollout is authorized here.
