## Provisioning: verified owner to one limited service lease

The proposed manager control subrouter uses actual requireManager, then additionally requires accountsEnabled(), nonempty validated sid, current verified/enabled account, isAccountSessionValid(sub,sid), unexpired signed claims and exact Registry.getManagerGame(pathGameId,sub). Body owner/sid/executor values cannot override these. Check again after any queue/transaction wait and immediately before committing the provisioning decision. Wrong/missing ownership returns a coarse denial without game/roster/lease metadata.

Owner, issuerSid and game come from that verified authority and actual Game. Provider/adapter selection must match the server's adopted configuration; the synthetic experiment permits only its synthetic adapter. Generate a stable opaque lease ID server-side. Use that ID as context.service, distinct from an adapter display name. Capture the existing facade's executorId. One authority UNIQUE(owner,game) remains in force across all providers/services; no second SQL partition can claim the same Game phone index.

Proposed lease authority record in a **new dedicated fixture-owned service-authority SQLite file**, not accounts/billing tables:

`(owner, game, provider, leaseId, issuerSid, executorId, initialActions, currentAllowedActions, fixedExpiresAt, currentCredentialVersion, capabilityHash, state, revokedAt, provisioningRequestId, requestFingerprint)`.

All records/queries include owner+game+provider, and provisioning request IDs bind the entire canonical request. Include game-wide uniqueness and durable provisioning/rotation receipts. Candidate address/lease existence is never an authorization result. No client body path selects a database.

Initial experimental scope is the four phone actions register/poll/answer/hangup only, never manager/account/game administration. The current store constructor requires register; arbitrary poll-only leases are **not** claimed supported. Per-action revocation is checked against currentAllowedActions at every boundary. Context.actions remains its original immutable upper bound; context.expiresAt remains its original lease expiry. An action policy preventing register may intentionally prevent reopening the current store. A more general read-only service factory would need a separately reviewed downstream port change.

Proposed short experimental lifetime is capped by both manager claims.exp*1000 and an explicitly reviewed short lease TTL, with no automatic extension. Actual session validation also denies a session whose DB expiry was shortened. Expiry/issuer-session replacement does not automatically reauthorize an existing game. The prototype's pinned issuer/service/expiry and terminal policy make transparent long-game renewal a separate design gate.

## Service credential issuance, delivery, replay and rotation

Choose **server-generated service capability with at-most-one secret-bearing issuance response attempt**, hash-only persistence, and fail-closed lost-response recovery. This is separate from the approved per-call capability, which stays gateway-generated and durably precommitted before REGISTER.

1. Under verified owner authority, generate32 random bytes for the service credential. Store only a purpose/scope/version-bound hash, fixed lease metadata and PENDING_DELIVERY state in a short transaction. Do not store plaintext, reversible ciphertext or a response containing the secret. No new server key/configuration is needed for hashing a random credential.
2. After commit and another live owner check, the initial control response may reveal that version's secret once. No credential in URL, receipt, log or exception; secret-bearing response is non-cacheable. A committed request retried under the same fingerprint returns only its durable provisioning status and secret_unavailable; it cannot reconstruct/reveal the secret. Changed fingerprint conflicts. Do not claim exactly-once network delivery: the server cannot know whether a response reached the operator.
3. The limited credential alone can acknowledge possession for its exact pending version through a separate service-control activation action. Recheck live issuer/account/Game, version and scope. Only then mark that version ACTIVE. Lifecycle actions reject PENDING_DELIVERY. Duplicate activation is idempotent and never echoes the secret. No store/controller mutation is implied by activating a credential.
4. Delivery from the owner response to a trusted gateway, and private durable storage before activation/use, remain **unimplemented and gated**. The experiment simulates that custody in a private fixture only. Possession of this service secret is not carrier/caller identity proof.
5. Lost issuance response or missing secret means an explicit authenticated owner rotation/revocation, not recovery from a hash or automatic second issue. Rotation atomically increments the credential version, revokes the old version immediately and creates a new PENDING_DELIVERY version. The old proof cannot retrieve even old receipts. No overlap/grace key is accepted. Same rotation request repeats its metadata receipt, without another secret or version; changed fingerprint conflicts.
6. Rotation retains stable leaseId, owner, issuerSid, Game object/executor, provider, initial action upper bound and fixed expiry so V2-A context/fingerprints remain compatible. It does not revive pending operations, retire unknown effects, alter predecessor generation or extend a session. Until new-version activation, all service actions deny. If that response is lost, explicit next rotation is again required. A new owner login may revoke its orphaned lease, but replacing the issuer on that same game needs separate reconciliation/adoption policy.

No claim is made that this is an implemented operator/gateway onboarding flow. For an eventual client-precommitted service secret alternative, the trusted client would need its own approved journal/delivery design first; the server cannot solve that by keeping a hash. This proposal selects the bounded lost-response behavior above rather than assuming secret retransmission.

## Authenticate each service request before lifecycle access

Use a distinct versioned service credential, not a manager JWT: a bounded canonical public address `(owner,game,provider,leaseId,credentialVersion)` plus the secret in Authorization, never a URL. Address fields are **untrusted lookup candidates** until the secret, live lease, issuer and Game all verify. Reject missing/malformed scope before storage. Owner/account identity never comes from phone/roster/call IDs.

The authority-store location is an explicit, preapproved fixed synthetic root, independent of unsigned candidate paths. One bounded authority lookup uses all candidate scope keys; compare the hash safely, including a dummy hash for an unknown row, and return one coarse external denial. The real account/session lookup is part of authorization too. **There is necessarily an authority lookup to authenticate an opaque credential; the guarantee is no lifecycle DB/path/registration/roster/receipt lookup before successful authorization**, not “no SQL whatsoever.” No implicit global/current-game/storage fallback is involved.

Following proof, require current ACTIVE version, unrevoked lease, expiry, current allowed action, active verified account, isAccountSessionValid(owner,issuerSid), and exact existing owned Game/executor. Then derive a frozen VerifiedServiceContext from server records. Ignore any client verified/owner/sid/actions/expiry/executor assertions. Run the scoped operation inside withAccount(verifiedOwner,...); verify the active account scope equals that owner before any tenant path use. In the experiment, inject an exact private fixture lifecycle root retaining the V2-A synthetic marker; no customer path resolver is added.

### Compatibility detail: do not cache the first request's proof

Both PrototypeStore and LifecyclePrototype retain a verifier function. Capturing the initial credential/version in that closure would reject every rotated credential, or incorrectly accept a cached old proof. Use one shared server-owned verifier and a private WeakMap from each newly derived context object to its verified request proof `(leaseId, version, supplied-proof digest, request lifetime)`. The map is populated only by the service adapter, never body deserialization; a fabricated/copied context has no provenance and denies.

Each callback uses that input context's proof, reloads current lease/version/action and actual account/session/Game state, and compares the supplied proof again. Context fields must still match the immutable store/facade binding. Retained context clones are configuration, not request authorization. Delete the map entry in request-finally; no raw manager JWT or service secret belongs in a cached store instance. A repeated HTTP request derives a fresh authorized context/proof. The same scoped verifier instance supplies both existing V2-A constructors; their current synchronous callback ports suffice for this experiment.

### Revocation boundaries and uncertainty

Recheck before opening a lifecycle store, inside each transaction after BEGIN IMMEDIATE can have waited, after reservation returns, before the synchronous Game invocation, before completion and before receipt disclosure. Do not hold a lease-authority write transaction while entering lifecycle SQL or Game; keep authority writes short and avoid lock-order cycles. The callback's account/lease checks are synchronous; no awaited work is inserted between final authorization/binding/epoch checks and the Game call in the owning executor turn.

If revocation is observed after a reservation, preserve its barrier. If it is observed after an effect but before completion/disclosure, do not assert no effect, automatically replay, hang up or roll back Game. A missing/corrupt authority DB, unknown version or missing Game also fails closed. A stored receipt is not an authority bypass.

Account DB, lease DB and Game heap are not one transaction. These checks prove revocation observed at the named boundaries; they do **not** prove instantaneous cancellation of an operation already authorized, nor linearizable cross-process revocation after the last check. A stricter requirement needs an explicit shared revocation/executor protocol. The next proof must name its boundary and capture actual effects instead of claiming that separate SQLite reads make Game mutation atomic.
